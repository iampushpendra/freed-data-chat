01 · System

Architecture

Three trust zones. Secrets never cross into the browser; the browser never reaches the VM; the VM is the only thing that touches the database. The VM has no inbound internet access—its firewall admits office/VPN only—so Vercel reaches it through a tunnel the VM dials outward.

02 · Request lifecycle

What happens when you ask a question

A single message runs an OpenAI tool loop: the model proposes SQL, the VM runs it read-only, the result feeds back, and the model writes the answer. Capped at 3 queries and a ~55 s budget so it always returns before Vercel's 60 s function limit.

sequenceDiagram
  autonumber
  participant U as Browser
  participant CH as /api/chat
  participant AI as OpenAI
  participant VM as query_api (VM)
  participant PG as Warehouse
  U->>CH: messages + auth cookie
  CH->>CH: verify HMAC cookie (else 401)
  CH->>AI: prompt + schema.md + run_sql tool
  AI-->>CH: run_sql("SELECT … LIMIT …")
  CH->>VM: POST /query + Bearer  (15s timeout)
  VM->>VM: validate: single SELECT/WITH only
  VM->>PG: read-only session · 60s · cap 2000
  PG-->>VM: rows
  VM-->>CH: {columns, rows, truncated}
  CH->>AI: tool result (rows)
  AI-->>CH: final answer (markdown)
  CH-->>U: {reply, tables[]}
  U->>U: render table + CSV + SQL disclosure

On a SQL error the VM returns 422 and the model self-corrects (still within the 3-query cap). If the VM is unreachable, the reply says so rather than hanging.

04 · Security

Four layers, one hard boundary

A bug in any single layer is contained by the next. The last layer is the one that makes a write physically impossible regardless of what the LLM emits.

LAYER 1 · access

Shared password + signed cookie

Only holders of the passphrase get a session. The cookie is HMAC-signed and HttpOnly—it can't be forged or read by scripts.

LAYER 2 · transport

Bearer secret, VM off the internet

Vercel→VM carries a bearer secret; the VM accepts inbound only from office/VPN and is reached via an outbound tunnel. No open DB port on the internet.

LAYER 3 · validation

SELECT / WITH-only validator

Single-statement guard; rejects DML/DDL, stacked queries, E'' escape strings, set_config, large-object & file functions. 90 unit tests.

LAYER 4 · hard boundary

Read-only Postgres session

Runs as a read-only BI user in a read only transaction with a 60 s statement timeout and a 2000-row cap. A write is impossible even if layer 3 were bypassed.

🛡️

Defense in depth, on purpose. Layers 3 and 4 are independent: the validator blocks the query class, and even a query that slipped past it lands in a transaction that cannot mutate data. A Critical stacked-query bypass found in review was closed at layer 3 before launch and re-verified against 14 exploit strings.

05 · Stack & scope

Choices & boundaries

Deliberately separate Vercel project

Its own project ID, so a deploy here can never overwrite the existing dashboard's auto-deploy pipeline.

No frameworks in the hot path

VM = Python stdlib http.server + psycopg2. Vercel functions = plain Node, zero runtime deps. Small surface, easy to audit.

Knowledge lives in one file

Widen what Analyst knows by editing context/schema.md and redeploying Vercel—no VM change needed.

v1 scope

Warehouse (Postgres) only; Mongo sources not exposed. 3 queries / message, 60 s, 2000 rows in-browser (full set in CSV).

Two known follow-ups

  • Tunnel is an interim *.trycloudflare.com quick tunnel (ephemeral URL). Upgrade to a stable named tunnel via vm/tunnel_setup.sh after one cloudflared tunnel login.
  • OpenAI key is currently reused from the sibling Note-Analyser tool; swap in a dedicated key by updating the Vercel env var.
